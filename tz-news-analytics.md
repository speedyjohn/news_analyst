# ТЗ: Новостной аналитик по официальным источникам

Версия 1.0 · черновик для согласования

---

## 1. Что делаем

Веб-приложение, которое:

1. Раз в сутки собирает новости с официальных источников (РК + зарубежье), сохраняет их и формирует дайджест «Топ-3 / Топ-5 / Топ-10 за день».
2. Позволяет зарегистрированному пользователю задать вопрос по новости. Нейросеть отвечает **только на основе официальных источников**. Вопрос живёт самостоятельно и может быть закрыт любой будущей новостью — тогда пользователю уходит письмо.
3. Отдельным модулем формирует юридически обоснованные предложения по изменению законодательства со ссылками на конкретные статьи.

Общее правило для любого ответа ИИ: **кратко, по делу, каждый тезис подкреплён ссылкой на официальный источник.**

## 2. Стек и архитектура

| Слой | Решение |
|---|---|
| Backend | Python 3.12, Flask (только JSON API), SQLAlchemy 2.0, Alembic |
| БД | PostgreSQL 16 |
| Планировщик | APScheduler внутри worker-контейнера |
| Frontend | React 18 + Vite, react-bootstrap (Bootstrap 5), SPA |
| LLM | Абстрактный провайдер: Claude / OpenAI / DeepSeek, выбор в конфиге |
| Почта | SMTP (любой провайдер), отправка асинхронно |
| Деплой | Docker Compose: `api`, `worker`, `db`, `web` (nginx со статикой React) |

### Структура backend

```
app/
  api/              # Flask blueprints — только HTTP, без логики
    news.py
    questions.py
    legal.py
    auth.py
    sources.py
  services/         # вся бизнес-логика
    ingestion.py    # оркестрация суточного прогона
    ranking.py      # оценка важности, формирование топов
    qa.py           # модерация вопроса, генерация ответа
    closure.py      # проверка открытых вопросов новыми новостями
    legal.py        # модуль законодательства
    notifier.py     # письма
  parsers/
    base.py         # BaseParser: fetch() -> list[RawArticle]
    rss.py          # универсальный RSS-парсер, настраивается из sources.yaml
    html/           # адаптеры под сайты без RSS (по одному файлу на источник)
  llm/
    base.py         # LLMProvider (ABC)
    claude.py
    openai.py
    deepseek.py
    factory.py      # выбор по конфигу
    prompts/        # промпты в отдельных файлах, не в коде
  models/           # SQLAlchemy-модели
  schemas/          # Pydantic — валидация входа и выхода API
  core/
    config.py       # pydantic-settings, всё из .env
    db.py
    security.py
  jobs/
    daily.py        # точка входа планировщика
```

Правила, которые соблюдаем с первого коммита, чтобы потом не переписывать:

- В `api/` нет обращений к БД и к LLM напрямую — только вызов сервиса.
- Парсер ничего не знает про БД: возвращает список объектов `RawArticle`, сохраняет `ingestion.py`.
- LLM вызывается только через `LLMProvider`. Ни одного прямого обращения к SDK провайдера вне `llm/`.
- Промпты — отдельные файлы, не строки внутри функций.
- Все внешние вызовы (HTTP, LLM, SMTP) идут через обёртку с ретраями и логированием.

## 3. Источники

Список хранится в `sources.yaml` в репозитории, при старте приложения синхронизируется в таблицу `sources`. На фронте есть страница «Источники» — только просмотр. Правка — через YAML и перезапуск (админку добавим позже).

Формат записи:

```yaml
- code: akorda
  name: Акорда — сайт Президента РК
  country: KZ
  category_hint: political_economic
  type: rss | html
  url: https://www.akorda.kz/ru/events
  feed_url: https://www.akorda.kz/rss   # если type: rss
  enabled: true
  parser: rss                            # или имя html-адаптера
```

### Кандидаты — Казахстан

| Код | Источник | Приоритет |
|---|---|---|
| `akorda` | akorda.kz — Президент РК | 1 |
| `primeminister` | primeminister.kz — Премьер-министр | 1 |
| `gov` | gov.kz — единый портал госорганов | 1 |
| `inform` | inform.kz — КазИнформ (гос. агентство) | 1 |
| `adilet` | adilet.zan.kz — НПА | 1 |
| `mazhilis` | mazhilis.parlam.kz | 2 |
| `senate` | senate.parlam.kz | 2 |
| `nationalbank` | nationalbank.kz | 2 |
| `stat` | stat.gov.kz — Бюро нацстатистики | 2 |
| `minfin` | Минфин РК | 3 |
| `mnec` | Миннацэкономики РК | 3 |
| `mfa` | МИД РК | 3 |

### Кандидаты — зарубежье

Берём **официальные площадки**, не медиа-агрегаторы.

| Код | Источник | Приоритет |
|---|---|---|
| `un_ru` | news.un.org/ru — Новости ООН | 1 |
| `ec` | ec.europa.eu — пресс-релизы Еврокомиссии | 2 |
| `imf` | imf.org — МВФ | 2 |
| `worldbank` | worldbank.org — Всемирный банк | 2 |
| `eaeu` | eaeunion.org — ЕАЭС | 2 |
| `whitehouse` | whitehouse.gov | 3 |
| `kremlin` | kremlin.ru | 3 |

### Порядок подключения

1. **День 1, первым делом** — прогнать скрипт `scripts/probe_sources.py`: для каждого URL проверить наличие `<link type="application/rss+xml">`, попробовать типовые пути (`/rss`, `/rss.xml`, `/feed`, `/ru/rss`). Скрипт печатает таблицу «источник → есть RSS / нет».
2. Всё, где RSS нашёлся, — включаем сразу через универсальный `rss.py`, без единой строки кода под конкретный сайт.
3. Всё остальное заносим в `sources.yaml` с `enabled: false` и комментарием `# требует html-адаптера`. Подключаем по мере необходимости — по одному адаптеру за раз.
4. В MVP достаточно **3–5 живых источников**. Из них обязательно `akorda`, `primeminister`, `inform`.

> Я намеренно не утверждаю в ТЗ, у кого RSS есть, а у кого нет — это проверяется скриптом за 15 минут и меняется без нашего участия. Архитектура от этого не зависит.

### Правила парсинга

- Запуск: ежедневно **07:00 Asia/Almaty**. Забираем материалы за предыдущие сутки (`published_at` в интервале).
- Берём **только русскоязычные версии**. Если у источника русской версии нет — сохраняем как есть, поле `language` фиксирует факт.
- Источник не ответил (таймаут, 5xx, невалидный фид) — **пропускаем, ретраев нет**, пишем запись в `ingestion_runs` с ошибкой. Прогон остальных источников не прерывается.
- Дубликаты: одна новость с двух источников сохраняется **только один раз**. Ключ дедупа — `content_hash` (SHA-256 от нормализованного заголовка: lowercase, убраны пунктуация и пробелы). Приоритет остаётся за источником с меньшим номером приоритета; вторая копия просто не сохраняется.
- Сохраняем полный текст.

## 4. Модуль 1 — Дайджест

### Обработка каждой новости при сохранении

Один LLM-вызов на новость возвращает JSON:

```json
{
  "summary": "2–3 предложения, сухо, без оценок",
  "category": "political_economic | other",
  "importance_score": 0-100,
  "importance_reason": "одно предложение — почему такая оценка"
}
```

Критерии важности (уходят в промпт дословно):

- масштаб последствий: сколько людей и отраслей затрагивает;
- уровень принятия решения: указ / постановление правительства / заявление ведомства / информационное сообщение;
- необратимость: принятый акт весомее анонса или обсуждения;
- финансовый масштаб: объём бюджета, тарифов, инвестиций;
- кадровые решения на уровне первых лиц;
- международные обязательства и договоры.

Протокольные и церемониальные сообщения (поздравления, приёмы верительных грамот) — не выше 20.

### Топы

- Топ считается **общий** — категория `political_economic` и `other` не разделяют выдачу, а показываются бейджем на карточке.
- РК и зарубежье тоже в одном списке.
- Топ-3 / Топ-5 / Топ-10 — это просто сортировка по `importance_score DESC` с лимитом за выбранную дату. Отдельной сущности «дайджест» в БД нет.
- Общая лента — сортировка по `published_at DESC`, пагинация по 20.

## 5. Модуль 2 — Вопросы

### Жизненный цикл

```
Пользователь задаёт вопрос к новости
      │
      ├─► LLM-модерация: этичность + релевантность
      │      └─ не прошёл → 400, вопрос НЕ сохраняется, пользователю текст причины
      │
      ├─► Сохраняем: status = open, привязка к исходной новости
      │
      ├─► LLM-ответ на основе нашей базы новостей → ai_answer
      │
      └─► Ежедневный прогон: новые новости проверяются против всех open-вопросов
             └─ закрывает → status = closed, official_answer, closing_news_id, письмо
```

### Доступ

- **Просмотр вопросов — публичный.** Список вопросов к новости и страница отдельного вопроса вместе с ответом ИИ и ответом официального источника доступны всем, включая неавторизованных посетителей. Вопрос — часть общедоступного контента новости, а не личная переписка.
- **Создание вопроса** требует авторизации.
- **Личная страница «Мои вопросы»** показывает только вопросы текущего пользователя. Это единственное место, где выдача фильтруется по автору.
- Автор вопроса отображается публично. В MVP — часть email до `@`; полноценные никнеймы вводить не будем, но поле `display_name` в `users` закладываем сразу, чтобы потом не мигрировать.
- Уведомление о закрытии вопроса уходит **только автору**, независимо от того, кто ещё этот вопрос смотрел.

### Модерация

Один вызов, JSON-ответ:

```json
{ "allowed": true, "reason": null }
```

Отклоняем, если: вопрос не относится к новости; содержит оскорбления, разжигание розни, призывы к насилию; просит инструкции для противоправных действий; является спамом или бессмыслицей. Отклонённые вопросы в БД **не пишем** (по решению заказчика; если позже понадобится статистика — добавим таблицу `rejected_questions`).

### Ответ ИИ

Контекст: текст исходной новости + до 10 наиболее близких новостей из базы (отбор по совпадению значимых слов заголовка и категории — без векторной БД, этого достаточно на текущих объёмах).

Ответ жёстко структурирован в два блока:

**Факты** — только то, что подтверждено источником из базы. Каждый тезис заканчивается ссылкой.
**Оценка** — если вопрос требует прогноза. Помечается явно: «Это предположение, а не официальная позиция». Прогноз обязан опираться на перечисленные выше факты, а не на общие рассуждения; в тексте прогноза указывается, из каких именно фактов он следует.

Если в базе нет данных — ответ: «В официальных источниках информации по этому вопросу пока нет». Придумывать запрещено, это отдельным предложением в промпте.

> Так закрывается пункт 2 исходного ТЗ (прогнозы и аналитика). Разделение на два блока снимает противоречие между «делай прогноз» и «каждый тезис со ссылкой»: факты подтверждены, вывод помечен как вывод.

### Закрытие вопросов

В ежедневном прогоне после сохранения новостей:

1. Берём все вопросы со `status = open`.
2. Предфильтр без LLM: пересечение значимых слов вопроса и текста новости (стоп-слова выкинуты). Отсекает основную массу пар бесплатно.
3. Прошедшие предфильтр отдаём LLM **пачкой**: одна новость + список вопросов-кандидатов → один вызов, JSON `[{question_id, closes: bool, official_answer: "..."}]`.
4. При `closes: true` — `status = closed`, заполняем `official_answer`, `closing_news_id`, `closed_at`, ставим письмо в очередь.

Закрытие автоматическое, без модерации. Если модель ошибётся — вопрос закроется неверно; это принятый риск, ручную отмену добавим вместе с админкой.

### Уведомления

Письмо на почту автора: тема вопроса, ответ официального источника, ссылка на закрывающую новость, ссылка на страницу вопроса. Отправка в отдельном потоке, ошибка SMTP не роняет прогон.

## 6. Модуль 3 — Предложения по законодательству

### Вход и выход

Пользователь описывает проблему свободным текстом («слишком короткий срок обжалования административного штрафа»). На выходе — юридическая записка, 1 страница:

1. **Суть проблемы** — 2–3 предложения, переформулировка своими словами.
2. **Действующее регулирование** — конкретные статьи с номером, названием акта и точной цитатой действующей редакции.
3. **В чём пробел** — обоснование, почему текущая норма проблему не решает.
4. **Предложение** — предлагаемая формулировка изменения. Оформляется как «изложить пункт N статьи M в следующей редакции: …».
5. **Обоснование** — почему предложенная редакция решает проблему.
6. **Дисклеймер** — фиксированный текст: материал носит рекомендательный характер и не является юридическим заключением.

### База законодательства

Разовым скриптом `scripts/load_legal.py` выкачиваем с adilet.zan.kz полные тексты ключевых кодексов, режем по «Статья N.» и складываем в `legal_articles`.

Стартовый набор (5 актов):

1. Кодекс об административных правонарушениях
2. Предпринимательский кодекс
3. Трудовой кодекс
4. Гражданский кодекс (Общая часть)
5. Налоговый кодекс

Расширение — добавлением кода акта в конфиг скрипта, без правки логики.

### Верификация ссылок (обязательно)

Модель **будет** выдумывать номера статей. Поэтому после генерации:

1. Из ответа регуляркой достаём все упоминания вида «статья N акта X».
2. Каждое проверяем по `legal_articles`. Статьи нет — ссылка невалидна.
3. Есть невалидные ссылки → **одна** повторная генерация с явным списком доступных статей в контексте.
4. Если и вторая попытка не прошла проверку — ответ пользователю не показываем. Вместо него: «Не удалось подготовить обоснованное предложение: нет достаточной опоры в загруженной базе НПА».

Ответ без единой валидной ссылки на статью не выдаётся никогда.

## 7. LLM-слой

```python
class LLMProvider(ABC):
    @abstractmethod
    def complete(self, system: str, user: str, max_tokens: int = 1500) -> str: ...

    @abstractmethod
    def complete_json(self, system: str, user: str, schema: dict) -> dict: ...
```

Реализации: `ClaudeProvider`, `OpenAIProvider`, `DeepSeekProvider`. Выбор в `.env`:

```
LLM_PROVIDER=claude
LLM_MODEL=claude-sonnet-4-5
LLM_API_KEY=...
LLM_TIMEOUT=60
```

Одна модель на все задачи (по решению заказчика). Разделение по типам задач заложено интерфейсом — при необходимости добавляется параметром, без переписывания вызовов.

`complete_json` сама снимает markdown-обёртку, парсит JSON, при ошибке парсинга делает один ретрай. Все вызовы логируются: задача, провайдер, токены, длительность.

## 8. Модель данных

**users** — `id`, `email` (unique), `display_name`, `password_hash`, `created_at`, `is_active`

**sources** — `id`, `code` (unique), `name`, `country` (KZ/foreign), `type`, `url`, `feed_url`, `parser`, `priority`, `enabled`, `last_success_at`

**news** — `id`, `source_id` → sources, `title`, `full_text`, `summary`, `url` (unique), `published_at`, `parsed_at`, `language`, `country`, `category` (political_economic/other), `importance_score`, `importance_reason`, `content_hash` (unique index)

**questions** — `id`, `user_id` → users, `news_id` → news (новость, с которой вопрос задан), `text`, `ai_answer`, `status` (open/closed), `official_answer`, `closing_news_id` → news (nullable), `created_at`, `closed_at`

**ingestion_runs** — `id`, `started_at`, `finished_at`, `source_code`, `status` (ok/failed), `items_found`, `items_saved`, `error`

**legal_acts** — `id`, `adilet_code`, `title`, `url`, `loaded_at`

**legal_articles** — `id`, `act_id` → legal_acts, `number`, `title`, `text`

**legal_requests** — `id`, `user_id`, `input_text`, `output_text`, `verified` (bool), `created_at`

Счётчик «0/4» в ленте считается запросом с группировкой по `news_id`, отдельного поля не заводим.

## 9. API

Все ответы — JSON. Ошибки в едином формате `{"error": {"code": "...", "message": "..."}}`.

`[public]` — доступно без авторизации, `[auth]` — требует JWT.

```
POST   /api/auth/register        [public]  {email, password}
POST   /api/auth/login           [public]  → JWT
GET    /api/auth/me              [auth]

GET    /api/news                 [public]  ?date=&top=3|5|10&page=&category=
GET    /api/news/{id}            [public]  новость + все вопросы к ней

GET    /api/news/{id}/questions  [public]  список вопросов к новости
GET    /api/questions/{id}       [public]  вопрос + ответ ИИ + ответ источника
POST   /api/news/{id}/questions  [auth]    {text} → 201 или 400 с причиной модерации
GET    /api/questions/mine       [auth]    только вопросы текущего пользователя

POST   /api/legal/suggest        [auth]    {text} → записка
GET    /api/legal/requests/mine  [auth]

GET    /api/sources              [public]  список источников (только чтение)
```

Единственные эндпоинты, фильтрующие выдачу по `user_id`, — `/questions/mine` и `/legal/requests/mine`. Везде остальное `user_id` на фильтрацию не влияет.

## 10. Frontend

React SPA, react-bootstrap. Экраны — см. отдельный документ `design-brief.md`.

Ключевое:

- Переключатель Топ-3 / Топ-5 / Топ-10 / Вся лента — сегментированные кнопки, состояние в URL (`?top=5&date=2026-09-03`), чтобы ссылка на дайджест шарилась.
- Карточка новости: бейдж категории, бейдж страны, оценка важности, счётчик вопросов `0/4`.
- Форма вопроса доступна только авторизованным; неавторизованному — кнопка «Войти, чтобы задать вопрос».
- Ответ ИИ рендерится двумя визуально разными блоками: «Факты» и «Оценка» (второй — с предупреждающим оформлением).

## 11. Аутентификация и лимиты

- Регистрация по email + пароль, JWT в httpOnly cookie. Подтверждения почты в MVP нет (флаг на будущее — до подключения публичной регистрации сделать обязательно).
- Лимиты на пользователя: **15 вопросов в сутки**, **5 в час**, **5 запросов в юридический модуль в сутки**. Реализация — таблица счётчиков или Redis-free вариант: считаем `COUNT(*)` по `created_at` за окно. Превышение → 429 с понятным текстом.
- Глобальный предохранитель: если суточное число LLM-вызовов превышает `LLM_DAILY_CALL_LIMIT`, новые пользовательские вызовы отклоняются, фоновый прогон — нет.

## 12. Конфигурация и деплой

Всё из `.env`: доступы к БД, ключ LLM, SMTP, секрет JWT, таймзона, лимиты, `INGESTION_HOUR`.

`docker-compose.yml`: `db`, `api`, `worker`, `web`. Сервер в РК. Миграции — Alembic, применяются на старте `api`.

Тесты в MVP не пишем (решение заказчика). Чтобы это не стало проблемой: вся логика лежит в `services/` чистыми функциями с явными зависимостями — покрыть тестами позже можно будет без рефакторинга.

## 13. План на 2 суток

**День 1**
- Утро: `probe_sources.py`, финальный список рабочих источников. Каркас проекта, Docker, модели, миграции.
- День: универсальный RSS-парсер, ingestion, LLM-слой + провайдеры, обработка новости (summary/category/score).
- Вечер: API новостей, каркас React, лента и топы.

**День 2**
- Утро: auth, модерация вопроса, генерация ответа, страница новости и вопроса.
- День: логика закрытия вопросов, письма, суточный прогон целиком.
- Вечер: юридический модуль (загрузка 5 кодексов, генерация, верификация), сборка, прогон на реальных данных.

**Что режем первым, если не успеваем** (в этом порядке):

1. Юридический модуль → переносим на день 3. Это самый ёмкий и самый рискованный блок: загрузка корпуса Adilet и верификация статей плохо сжимаются.
2. Письма → закрытие вопроса просто отображается в интерфейсе.
3. Зарубежные источники → оставляем только РК.

Скажу прямо: весь объём за 2 суток — очень плотно, при условии что не всплывут сюрпризы с вёрсткой госсайтов. Пункты 1–3 в 2 дня реалистичны. Юридический модуль честнее сразу планировать на день 3.
